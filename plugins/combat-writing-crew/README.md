# Combat Writing™ Crew: the add-on

**Reading is Peace. Writing is War.**

The Combat Writing plugin, `cw`, seats two fresh readers from one company. This add-on seats other companies' models in the second chair, one seat per model you hold a key for, on your own API keys, so a round can be read by more than one company: the moment it seats one, the `cw` plugin's second fresh reader leaves and the outside seats number from 2 (Part 87). The crew is never padded: with one free Groq key it is three seats, seat-1, Qwen as seat-2 and gpt-oss as seat-3; an xAI key seats Grok, a Google key Gemini, each key the model of its provider, resolved from that provider's live catalog. It is a local MCP server, built for **Claude Code**: a local MCP server is ignored in chat on claude.ai and loads in the desktop app only on your own computer. Install it from the Claude plugin directory once it is listed there, or from this repository as Learning Producers' own marketplace. The add-on is source-available under the same terms as the `cw` plugin.

## What it does

- `crew_list` says which outside seats are available with the keys you set, each named by the model id resolved from the provider's live catalog and by the model's maker, with the serving provider stated.
- `crew_register` adds those seats to a run's `seats.json`, so the `cw` plugin builds their packets like any seat's, and writes on each seat the wall it spends from (`budget`: per_minute, reply_floor, reply_ceiling, the add-on's own budget for that provider, below), which the `cw` plugin's `budget.js` reads to measure, before any seat starts, the room a round's packets leave, and to warn when a seat will be refused.
- `crew_answer` sends one seat's packet for one round to its provider, with the packet's word cap and first-line contract stated in the system line, waits out the per-minute window, writes the answer file beside the packet, and logs the model id the API returned, when it has the shape of one. The `cw` plugin's checks, battle, final reads, record and board then work across companies with nothing copied by hand.

A seat that fails, has no key, or whose packet is too long to send is shown as missing, never silently replaced. Nothing is faked.

## The word cap

Every packet states its cap: 500 words for a read alone, 600 when other seats' answers are carried, 250 for a final read. The add-on repeats the number in the system line it sends, so the outside seat knows the cap before it writes. An answer over the cap fails the `cw` plugin's check and the host sends the seat back once, with the reasons in `note`; the reason names the retry target, 80% of the cap, and the add-on's retry line repeats it. If that second answer is over the cap again, the add-on cuts it at the cap: the contract's first line (`RATING: X/10`, or the S/N or red-flag line) is pulled out of the reply wherever the seat put it and kept at the top, the rest is cut at the last sentence end before the cap (at a word boundary when no sentence ends in the last sixty words) so the file counts no more than the cap, and the log line says `truncated` with the word counts. The record and the board mark that read "truncated at N words" with the rating shown. A read in a round that asked for no rating is cut the same way with no line to keep. The `cw` plugin's checker makes the same cut for its fresh reader, so one rule holds for every seat. The answer file holds only the seat's own words; the mark lives in the log. When the packet says no seat can open a link (the `cw` plugin's line, mirrored in `crew-lib.js`), the system line says it too: links are unread, and the seat never states what a page says.

## Install

In Claude Code:

```
/plugin marketplace add LearningProducers/CombatWriting-Plugin
/plugin install combat-writing-crew@learning-producers
```

Or in one step, on Claude Code 2.1.275 or later:

```
/plugin install combat-writing-crew --marketplace LearningProducers/CombatWriting-Plugin
```

Node must be on your PATH: the add-on's server is started with `node`. Its checks were run on Node 22, and on no other version.

Install the `cw` plugin the same way; the add-on does nothing on its own.

## Keys and where the prompt appears

Each key goes only to its own provider. No key is ever sent to Learning Producers, written to a file by the add-on, or logged. A key reaches the add-on from two places and no other, the masked prompt first and then your own key file:

1. **The masked prompt.** When you install or enable the add-on in Claude Code, a dialog asks for each key with the input masked; the value goes to Claude Code's secure credential store (the macOS Keychain, or `~/.claude/.credentials.json` where there is none), keyed by the plugin's id, not to a settings file. Reopen it any time with `/plugin configure combat-writing-crew`. Every key is optional: leave the ones you do not have empty. A plugin version bump keeps the stored key; the host rebuilding its credentials store does not (measured 2026-10-19 on Claude Code 2.1.303: the store was recreated at a session start after a host update, and the key went with it while the install stood). When that happens the crew says so and the key is typed in again; a save with nothing typed says "No configuration changes" and keeps nothing.
2. **Your own key file, only when the prompt's value is empty.** One file, `~/.combat-writing/keys`, in your home folder, written by you by hand in a Terminal and never through a tool call (a key typed into a tool call lands in a transcript), holding `NAME=value` lines, `#` comments and blank lines allowed. The names, one per provider: `GROQ_API_KEY`, `XAI_API_KEY`, `PERPLEXITY_API_KEY`, `OPENAI_API_KEY`, `MISTRAL_API_KEY`, `GEMINI_API_KEY`. The server reads it only when it is a regular file whose mode gives group and others nothing (600), in a folder whose mode gives them nothing either (700); a file open to others, a symlink, or a line that is not `NAME=value` is refused whole, and the crew says why, naming the mode or the line number and never a line's content. A `.env` or a key file beside your project is still never opened. To write it on macOS, with the key on the clipboard:

```
mkdir -p ~/.combat-writing && chmod 700 ~/.combat-writing
(umask 077; printf 'GROQ_API_KEY=%s\n' "$(pbpaste)" > ~/.combat-writing/keys)
ls -l ~/.combat-writing/keys
```

The `ls` line must read `-rw-------`. Then start a new session; the add-on reads the file at every call.

**A key in your shell is not read.** A key that stands only in a provider's usual variable in your shell, `OPENAI_API_KEY` and the like, is not read by the add-on and seats nothing: enter it once, in the masked prompt or in the key file. The names above are the names of lines in the key file and nothing else. So the add-on sends nothing to any provider until you have put a key in one of the two places yourself.

**Why the key file exists.** The key file exists because it is the route that survives a host update: the host's credentials store, where the masked prompt keeps a key, has been rebuilt by an update with the key gone, and nothing rebuilds a file. The masked prompt is the first place and the shape the Claude plugin directory asks for. The key file is the fallback: it holds a key you put on your machine for this add-on, and the add-on sends it only to its own provider, which the directory's checklist holds for a reviewer to read. A key the store drops falls through to the file and the seat stays.

**Where a key lives, measured (Part 36.1, 2026-10-20, Claude Code 2.1.304 through 2.1.310).** The masked prompt's value goes to the host's credentials store (on macOS a Keychain item keyed by the plugin's id) and reaches the server as an empty string when unset or dropped. The host rebuilt that store on 2026-10-16 and again on 2026-10-24, each on a Claude Code update, and the key went with it both times while the install and the manifest stood; the crew ran one seat until a board showed it. A provider's usual variable in your shell is visible to every process you run, is often copied into logs, and was put there for other tools; the add-on leaves it alone. The key file survives the host, carries a mode that gives group and others nothing, and is never rebuilt by anything; its permissions are the floor and the add-on refuses it when they are not owner-only. That is why the read order is prompt, then file: a key lost from the store falls through to the file and the seat stays. The add-on is a local MCP server and reads the file outside any shell sandbox; a sandboxed shell in the same session may be denied the path by its own settings, which is the point.

**Where it runs.** The add-on is built for **Claude Code**, in the terminal, the IDE extensions and the desktop app's Code tab: Claude Code starts the server and shows the masked prompt (the install dialog, the VS Code extension's form, and `/plugin configure`). A local MCP server is ignored in chat on claude.ai and loads in the desktop app only on your own computer; in chat the add-on does not run, and the crew is one seat, the host. **Cowork** does not prompt for plugin options, and the directory's platform-support page says it ignores a server whose options have no default, which is every key option here; that line is read from the page, not measured, so count on Claude Code.

A crew with no paid keys is allowed: one free Groq key seats two outside models (OpenAI's open-weight line and Alibaba's Qwen line, both served by Groq) beside the `cw` plugin's first fresh reader, a crew of three (its second fresh reader leaves when the first outside seat registers). Every further key adds one seat, numbered after those in the add-on's provider order.

## When a seat you expected is missing

Every result of the `cw` plugin names the reason and the exact next command when the crew is short, in a Seats line under the crew line. Three states:

1. **Not installed.** The host has no crew tools and `claude plugin list` does not show `combat-writing-crew`. Next: `/plugin install combat-writing-crew --marketplace LearningProducers/CombatWriting-Plugin`, then `/reload-plugins` or a new session, then `/plugin configure combat-writing-crew`.
2. **Installed, server not running.** The host has no crew tools but `claude plugin list` shows the add-on. Next: `/mcp`, find `combat-writing-crew`; if it shows failed or disconnected, reconnect it there and run the command again; if it is not listed, `/plugin` to check the add-on is enabled, then `/reload-plugins`.
3. **Running, no key.** `crew_list` returns the seat as unavailable with a `reason` that names the two causes a person can hit (the key was never entered, or an update dropped it when the host rebuilt its credentials store) and the one next step, with `next` (`/plugin configure combat-writing-crew`), `field` (the option to type the key into, such as `groq_api_key`), `field_title` (as the prompt shows it, such as "Groq API key") and `key_shape` (`empty`, what the host hands for an option it does not hold; or `placeholder`, the literal `${user_config.<option>}` handed unfilled, which the server reads as no key and never sends), names only, never a value; `key_name` and `file` name the key file's line and its path, and `key_shape` reads `file-refused`, with the reason in `reason`, when a key file is there and was refused (its permissions, or a malformed line named by number); `crew_register` logs the same, and the record prints it. A keyed provider that did not answer is listed with its error.

## Which models

No model id is written in the add-on. For each provider, a seat names a family and a preference, and the server resolves the id from the provider's live catalog at the start of a run: for Groq, the newest live model in Alibaba's `qwen/` line as the first outside seat (seat-2) and the largest live model in OpenAI's `gpt-oss` line as the second (seat-3), the Qwen seat first (issue 86; a per-user order is not built), excluding speech, guard, compound and embedding models and anything with a small context window, the same filter the Combat Writing app uses. A name from a provider is taken only in its shape. An id from the list, and the model field of a reply, must be a model id: letters, digits, dot, dash, underscore, slash, colon and square brackets, at most 120, no space and no line break. A maker must be a plain name that opens with a letter or a digit: at most four words of letters, digits and . & ' ( ) -, 40 characters in all. An id in another shape is not offered, a maker in another shape reads `maker not reported`, and a reply's model field in another shape leaves the seat's name as it was and is logged as refused, with none of its text. Every answer's log line carries the id the API returned, and the seat's name follows it, when it is a model id.

| groq-a | Groq | OpenAI's open-weight line, largest live | OpenAI |
| groq-b | Groq | Alibaba's Qwen line, newest live | Alibaba |

## What it sends where

- To each provider, over HTTPS (the local Ollama seat alone over plain HTTP, on your own machine): the seat's packet, whole, as the `cw` plugin wrote it. You can read it before it goes: it is the file `rounds/<round>/<seat>.packet.md` in the run folder (`<seat>.sn.packet.md` and `<seat>.redflag.packet.md` for the final reads, `<seat>.crew.packet.md` for a second pass), built before any seat starts. A packet carries the task and its contract, the brief, who the piece is for when you gave a reader, the draft fenced as untrusted content with its counts and its parts as code measured them, the seat's own earlier turn, the other seats' answers from the previous round when the round shares them, and your guidance or question; on a retry the host's note, the failed check's reasons, is added after the packet. With the packet go a short system line naming the seat, its first-line contract and the word cap, the model id and the reply's size limit, and your key for that provider in the request header. Before a run, the read of a provider's model catalog carries your key and nothing of your writing.
- To your project: the answer file beside the packet, the seat's entry in `seats.json`, and one log line per event in `log.jsonl` (timestamp, provider, the model id requested and the id returned, the cap and contract sent, whether the reply was truncated, token counts the provider reported, when they are whole numbers from 0 to a thousand million, how long the server waited, and which place the key came from, `prompt` or `file`, never a key). A provider's error text, and the message of any error the server itself raises, is scrubbed before it lands anywhere (measured 2026-10-24: Groq's refusals name the organization the key belongs to): the key in use, whatever its shape, becomes `[key redacted]` every time it appears; account-id tokens (`org_…`, `user_…`, `proj_…`, `acct_…`, `team_…`, `key_…`, and the hyphenated forms OpenAI's ids take) become `<kind>_[redacted]` and key-shaped strings (`sk-…`, `gsk_…`, `xai-…`, `pplx-…`) become `[key redacted]`, in the log line, the tool result the host reads and the server's own stderr alike, and so in the record and the board the `cw` plugin renders from the log. The key rides in a request header the add-on never echoes; a provider that echoes it in a refusal is why the key in use is removed by its exact text and not by its shape alone. A provider's error text is then made one line and cut at 300 characters before it stands in a reason.
- To Learning Producers: nothing. The add-on makes no call to any address but the provider's.
- From your shell's variables: no key, ever. The server reads `OLLAMA_MODEL`, the Ollama seat's model when the option is empty, and one variable that exists for the add-on's tests, `CW_CREW_KEY_FILE`, which moves the key file's path; the add-on does not set it, and without it the path is `~/.combat-writing/keys`. Nothing moves the provider table, the list of hosts a key can be sent to: it is the `providers.json` in the add-on's own folder, whatever your shell or your project holds.

## Rate limits and size

The server keeps the Combat Writing app's call budget for each provider: an 8,000-token per-minute wall, a 1,200-token reply floor and a 2,800-token reply ceiling, with input estimated at four characters per token. A packet that leaves less than the floor for a reply is refused before anything is sent, with the app's message, "Too long to send", naming the number as this add-on's budget for that provider, not a limit the provider set, and how much to cut. The server tracks what it sent to each model at a provider in the last sixty seconds and waits before a call that would cross that model's wall or request limit; on a 429 it waits the provider's `Retry-After` (at most seventy seconds) and tries once more, then records the seat as missing. Calls to one model go one at a time; two seats on two models at one provider go side by side. The wall is the model's, not the provider's (issue 93, measured 2026-10-27): Groq's refusal names the model it refuses for, and one window per provider had made the second Groq seat wait the first seat's minute out on every round that carried other seats' answers (59, 57 and 50 seconds on three packets of one run). If a provider's wall turns out shared, the second call lands on the 429 path above and costs that one wait.

A 429 on the provider's per-minute output limit is different, and the server reads it as such (measured 2026-10-24 on Groq's free tier: `on output tokens per minute (OTPM): Limit 1000, Requested 1513`, the provider's forecast of one request's output held against its per-minute limit). No wait helps there: the same body sent again a minute later draws the same refusal, and a request that asks for less than the limit is accepted. The server reads the limit and the requested count from the message, lowers `max_tokens` to the limit under a 5% margin (or by the limit-to-requested ratio when that is lower), and resends at once, once; the log line and the result carry `max_tokens_lowered` with the four numbers. The limit, not the ratio, is the number (measured 2026-10-27, issue 78): the same packet shape with `max_tokens` 2800 drew "Requested" 1513, 2055 and 1039 from Groq on three days, so its count is not `max_tokens` scaled, and a resend lowered by the ratio landed above the limit and was refused again, the seat missing twice. The seat is kept whenever the limit itself covers what the reply needs (1.6 tokens a word plus 40 for the first line: 1,000 tokens for a 600-word cap, 840 for 500, 440 for 250): on a limit of 1,000 a 600-word packet is resent at 950, because the margin is the resend's safety and never a reason to drop a seat, and 1.6 is a ceiling most replies run under. Only when the limit itself is under that need is the seat missing this round, and the reason names the provider's per-minute limit and what the reply needs, so the next step is a paid tier or a smaller cap. A reply the provider stops at `max_tokens` (the API's `finish_reason` reads `length`) is still written: the log line carries `finish_reason` and `stopped` (the tokens the call asked for, the tokens returned, and the lowering when there was one), the result says so, and the `cw` plugin's record and board mark the read "stopped at N tokens", beside the truncated mark and never in its place. An empty reply the provider stopped is missing, with where it was stopped in the reason. Every `crew.failed` and `crew.refused` line carries the read and its reason, and the record and the board show that reason under the missing seat, so nobody opens the log to learn why a seat did not answer. A 429 on total tokens per minute, and any other 429, keeps the wait above.

Groq's free tier, as the app documents it: 8,000 tokens and 30 requests per minute, 1,000 requests per day, and Groq counts the reply reservation as well as the input. Each Groq model has that minute to itself. A sparring packet costs about 3,600 tokens of window (a short input plus the 2,800 reply ceiling); an SN or SFQ packet carries the other seats' answers and costs about 5,300 to 7,700, which still fits one model's minute, so the two Groq seats answer a sharing round together; an N packet carries no other seat and costs about what a sparring packet does; the final reads (two packets per seat) take about two minutes at each model's wall, the two seats side by side. A packet that pastes a long page beside carried answers can leave less than the 1,200-token floor for a reply, and then the seat is refused before anything is sent with how much to cut. The server waits by itself; nothing is lost, only time. The price of every round is measured once its packets are built, before any seat starts: the `cw` plugin's `budget.js` reads the wall from each seat's record and the packets' sizes, puts the largest packet's estimated tokens by part and the room left on the board under Run details and in the record, and prints one warning on the terminal only when a seat's packet will be refused, naming the seat and by how much, so "Too long to send" never comes after the send. The one other line it can print is for a fresh reader's packet over the size the `cw` plugin counts on for one read; it names no outside seat.
