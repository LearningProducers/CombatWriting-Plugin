# CLAUDE.md — working rules for this repository

This repository is the home of the Combat Writing™ plugin for the Claude plugin directory, named `cw` (its commands are `/cw:strategy`, `/cw:sparring`, `/cw:battle`, `/cw:champion`, `/cw:help`, `/cw:briefs` and `/cw:runs`; it was `combat-writing` until 2026-10-14, and the marketplace's `renames` map migrates installs under the old name), and of its local add-on, `combat-writing-crew`, submitted to the Claude plugin directory as a second bundle from this repository (PLAN.md Part 107, issue 221, ruled 2026-11-17). Learning Producers Inc. (LPI) owns it. Israel Hernandez, LPI's founder, merges. A build session opens pull requests. PLAN.md is the only memory between sessions.

The motto is "Reading is Peace. Writing is War." It is brand. It is never softened.

## Standing rules

- Open a pull request; never merge. One pull request per part, one change per pull request. The pull request body carries the four sections (ruled 2026-10-14, below): CI cuts the Release notes from WHAT CHANGED.
- Bump before opening the pull request (ruled 2026-10-12): a change to any file under `plugins/combat-writing/` bumps the version in that plugin's `plugin.json` and in its `marketplace.json` entry; the same for `plugins/combat-writing-crew/`, and a change to any file under `screen/` (its tests included) bumps the version in `screen/pyproject.toml`, by the session's own hand the `cw-screen` entry of `screen/uv.lock` so the two agree (Part 44; measured 2026-11-02 on pull request 136, whose fixture change went red on the gate), and `__version__` in `screen/cw_screen/__init__.py`, the string `cw-screen --version` prints, the third file (issue 149, 2026-11-04: it sat at 0.1.2 through the 0.1.3 and 0.1.4 bumps; `screen/tests/shell_check.py` pins it equal to `pyproject.toml`, so the suite goes red when either moves alone). Changes outside those three folders (docs, CI, tests/) need no bump. CI fails a pull request that forgot, naming the folder; for `screen/` the gate reads `pyproject.toml` alone, and `uv sync --frozen` does not compare the lock to it, so the lock's entry is checked by no gate; `__init__.py` is held by the test alone. On each push to main, CI tags every plugin version not yet tagged on origin as `<plugin-name>--v<version>` with the message `<plugin-name> <version>`, the name read from the manifest (the listed plugin is `cw`, in the folder `plugins/combat-writing/`), the name and message `claude plugin tag` produces; an already-tagged version is a no-op. ## The pull request

**The four sections** (founder ruling 2026-10-14). Every pull request body carries four headings in this order, each with text under it, each in words a non-coder rules on, because the founder merges on the four sections alone: WHAT CHANGED, what a reader sees differently after the merge (CI cuts the Release notes from it); WHY, the ruling, the issue or the problem it answers; HOW IT WAS TESTED, what ran, where, what it proved, and what did not run; WHAT COULD BREAK, what to watch after the merge and how one would notice, "Nothing known" when that is true. The template `.github/PULL_REQUEST_TEMPLATE.md` lays them out with hints as HTML comments, so an unfilled section reads empty; the footer `DOCS OWED: none`, or what is owed, closes the body and is no section's text. The `pr-body` check (`.github/workflows/pr-body.yml`, the script `.github/scripts/pr-body.js`) fails a pull request whose body misses a heading or leaves a section empty, naming the section; it reruns on every edit of the body, so a fix in GitHub's editor turns it green with no push. A session never opens a pull request red on pr-body: it runs the body through the script before `gh pr create` and reads the check after.

**One change per pull request** (Google's engineering practices, Small CLs). One issue, one change, one pull request a reviewer can describe in a sentence. A second change found on the way, a fix beside the task, a cleanup, a rule that turned out wrong, opens its own issue and its own pull request; it never rides on this one.

**The issue closes on merge** (founder ruling 2026-10-19). Every pull request body carries `Closes #N` for the issue it resolves, one line per issue, so the merge closes it; the founder never closes an issue by hand. The line sits under WHY, where the issue is named, and is no section's whole text. A pull request that resolves no issue says so in WHY. Issues 13 and 36 were resolved by pull request 37, which merged before this rule and carried no such line; they stay open until a pull request that touches them carries `Closes #13` and `Closes #36`, or the founder rules otherwise.

## Terms

- A **seat** is one model judging the draft.
- The **crew** is all seats.
- The **host** is the Claude the person talks to.
- A **fresh reader** is a separate Claude started for one job (an agent).
- A **packet** is everything one seat is sent for one round.
- A **flip** is a seat changing its rating after reading the others.
- The **credit line** is the Required Notice text: "Combat Writing — Learning Producers Inc., Israel Hernandez, founder". It stands at the foot of the card and at the foot of the guide, `/cw:help` bare and `/cw:help all`, with the site after it (issue 158, 2026-11-04); no run output, record or board carries it (ruled 2026-10-12).

## Licensing by path

- **PolyForm Shield 1.0.0** (`LicenseRef-PolyForm-Shield-1.0.0`): every executable file: scripts, skill files (the seven commands among them), agent definitions, prompts, plugin configuration, tests, workflows, and the Markdown files outside the CC paths (README, CONTRIBUTING, CLAUDE.md, PLAN.md, PLAN_ARCHIVE.md, RULINGS.md). PolyForm Shield is not on the SPDX license list, so the identifier takes the SPDX form for an unlisted license. The text is verbatim from the PolyForm Project's repository (polyformproject/polyform-licenses, PolyForm-Shield-1.0.0.md, commit 76a278c).
- **CC BY-NC-SA 4.0** (`CC-BY-NC-SA-4.0`): methodology prose and documentation under `docs/` and under `plugins/combat-writing/method/`. The text is verbatim from the SPDX license-list-data repository (text/CC-BY-NC-SA-4.0.txt, commit 31ba1a5).
- Never both on one file.
- Header on every file that can carry a comment. JSON files get none; the `license` field in plugin.json covers that manifest. `NOTICE`, `LICENSES/`, `plugins/*/LICENSE*`, images and fonts carry none.

Header formats (exactly one header per file, on line 1 for a plain file):

```
JavaScript:  // SPDX-License-Identifier: LicenseRef-PolyForm-Shield-1.0.0
YAML:        # SPDX-License-Identifier: LicenseRef-PolyForm-Shield-1.0.0
Markdown:    <!-- SPDX-License-Identifier: LicenseRef-PolyForm-Shield-1.0.0 -->
```

A Markdown file with YAML frontmatter (skills, commands, agents) keeps the frontmatter on line 1, because the loader reads it only there, and puts the comment on the line after the closing `---`. No other position is accepted.

`tests/license_check.js` enforces all of this. Run it from the repository root: `node tests/license_check.js`.

## Directory constraints

Read on 2026-10-08 from the pre-submission checklist (claude.com/docs/plugins/pre-submission-checklist) and the publish page (claude.com/docs/directory/publish). LICENSE file or `license` field in plugin.json. README in the plugin folder over 40 words outside code blocks with at least three working example prompts. Every non-image file under 256 KiB. No lockfile beside a package.json at the plugin root. No top-level bin/. No .pdf, .zip or binaries. Any package launcher pinned to an exact version or absent. The plugin may be a subfolder. Everything the plugin runs lives inside it. No implication of Anthropic endorsement. The method text ships inside the plugin, never fetched.

The manifest description follows the directory policy line "Descriptions must not include unexpected functionality or promise undelivered features" (Anthropic Software Directory Policy, support.claude.com). It promises only what parts 2 to 4 deliver.

## Test style

Plain Node, no dependencies, one file per concern named `*_check.js` (two exceptions, the live proofs, which need a running Claude Code and are never run by CI: `tests/seat_scope_live.js`, the seat's reach, and `tests/session_start_live.js`, the data folder the session-start hook is handed), a header comment that says what the test pins and how to run it, run from the repository root, exit 0 on pass and 1 on any failure, one printed line per failure. A test of a network client runs it against a fake server on localhost, never a real provider. CI runs every `tests/*_check.js` on each pull request and on main, then `claude plugin validate --strict` on both plugin folders and on the repository root; on a pull request the version-bump gate runs before the checks, and on a push to main the `tag` job (tags, then a Release for each tag without one) follows them. CI's `screen` job runs the screen's tests, `screen/tests/*_check.py` (Python, the same shape: one file per concern, exit 0 or 1, one line per failure), on the committed lock through uv; they build runs with the plugin's real scripts, so a change to how a run is seated or rendered reaches them too. One command runs the set CI runs, and a local pass is its exit 0 (Part 88, 2026-11-02; origin: pull request 136 passed the plugin's tests and the watchman locally and went red in the screen job): `node tests/run_all.js`, the plugin's tests, then the screen's through uv (a missing uv is a failure unless `--no-screen` says the skip is meant), then `claude plugin validate --strict` on the three folders when the CLI is on the PATH (skipped with a line when not). A session runs it before every pull request.
