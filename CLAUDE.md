# CLAUDE.md — working rules for this repository

This repository is the home of the Combat Writing™ plugin for the Claude plugin directory, named `cw` (its commands are `/cw:strategy`, `/cw:sparring`, `/cw:battle`, `/cw:champion`, `/cw:help`, `/cw:briefs` and `/cw:runs`; it was `combat-writing` until 2026-10-14, and the marketplace's `renames` map migrates installs under the old name), and of its local add-on, `combat-writing-crew`, submitted to the Claude plugin directory as a second bundle from this repository (PLAN.md Part 107, issue 221, ruled 2026-11-17). Learning Producers Inc. (LPI) owns it. Israel Hernandez, LPI's founder, merges. A build session opens pull requests. PLAN.md is the only memory between sessions.

The motto is "Reading is Peace. Writing is War." It is brand. It is never softened.

## Standing rules

- Open a pull request; never merge. One pull request per part, one change per pull request. The pull request body carries the four sections (ruled 2026-10-14, below): CI cuts the Release notes from WHAT CHANGED.
- Bump before opening the pull request (ruled 2026-10-12): a change to any file under `plugins/combat-writing/` bumps the version in that plugin's `plugin.json` and in its `marketplace.json` entry; the same for `plugins/combat-writing-crew/`, and a change to any file under `screen/` (its tests included) bumps the version in `screen/pyproject.toml`, by the session's own hand the `cw-screen` entry of `screen/uv.lock` so the two agree (Part 44; measured 2026-11-02 on pull request 136, whose fixture change went red on the gate), and `__version__` in `screen/cw_screen/__init__.py`, the string `cw-screen --version` prints, the third file (issue 149, 2026-11-04: it sat at 0.1.2 through the 0.1.3 and 0.1.4 bumps; `screen/tests/shell_check.py` pins it equal to `pyproject.toml`, so the suite goes red when either moves alone). Changes outside those three folders (docs, CI, tests/) need no bump. CI fails a pull request that forgot, naming the folder; for `screen/` the gate reads `pyproject.toml` alone, and `uv sync --frozen` does not compare the lock to it, so the lock's entry is checked by no gate; `__init__.py` is held by the test alone. On each push to main, CI tags every plugin version not yet tagged on origin as `<plugin-name>--v<version>` with the message `<plugin-name> <version>`, the name read from the manifest (the listed plugin is `cw`, in the folder `plugins/combat-writing/`), the name and message `claude plugin tag` produces; an already-tagged version is a no-op. A tag that already has a Release is a no-op. A build session never tags.

## The pull request

**The four sections** (founder ruling 2026-10-14). Every pull request body carries four headings in this order, each with text under it, each in words a non-coder rules on, because the founder merges on the four sections alone: WHAT CHANGED, what a reader sees differently after the merge (CI cuts the Release notes from it); WHY, the ruling, the issue or the problem it answers; HOW IT WAS TESTED, what ran, where, what it proved, and what did not run; WHAT COULD BREAK, what to watch after the merge and how one would notice, "Nothing known" when that is true. The template `.github/PULL_REQUEST_TEMPLATE.md` lays them out with hints as HTML comments, so an unfilled section reads empty; the footer `DOCS OWED: none`, or what is owed, closes the body and is no section's text. The `pr-body` check (`.github/workflows/pr-body.yml`, the script `.github/scripts/pr-body.js`) fails a pull request whose body misses a heading or leaves a section empty, naming the section; it reruns on every edit of the body, so a fix in GitHub's editor turns it green with no push. A session never opens a pull request red on pr-body: it runs the body through the script before `gh pr create` and reads the check after.

**One change per pull request** (Google's engineering practices, Small CLs). One issue, one change, one pull request a reviewer can describe in a sentence. A second change found on the way, a fix beside the task, a cleanup, a rule that turned out wrong, opens its own issue and its own pull request; it never rides on this one.

**The issue closes on merge** (founder ruling 2026-10-19). Every pull request body carries `Closes #N` for the issue it resolves, one line per issue, so the merge closes it; the founder never closes an issue by hand. The line sits under WHY, where the issue is named, and is no section's whole text. A pull request that resolves no issue says so in WHY. Issues 13 and 36 were resolved by pull request 37, which merged before this rule and carried no such line; they stay open until a pull request that touches them carries `Closes #13` and `Closes #36`, or the founder rules otherwise.

## Terms

- A **seat** is one model judging the draft.
- The **crew** is all seats.
- The **host** is the Claude the person talks to.
- A **fresh reader** is a separate Claude started for one job (an agent).
- A **packet** is everything one seat is sent for one round.
- A **flip** is a seat changing its rating after reading the others.
- The **credit line** is the Required Notice text: "Combat Writing — Learning Producers Inc., Israel Hernandez, founder". It stands at the foot of the card and at the foot of the guide, `/cw:help` bare and `/cw:help all`, with the site after it (issue 158, 2026-11-04); no run output, record or board carries it (ruled 2026-10-12).

## What is ruled about the method

How to read this section. Each bullet is one rule. Its closing clause names what holds it. `Held by: tests/<name>_check.js.` names the tests that fail when the rule is broken; the bullet is then the rule in short, and a sentence inside it that no test holds is kept in its own words and is the rule all the same. `Held by: its words.` means no test fails when the rule is broken; the bullet is then the rule whole, and reading it is the only thing that keeps it. Before changing a rule or the code under it, read its entry in `RULINGS.md`, found by the bullet's lead words: the entry is the record, who ruled it, when, in which issue or part, what was measured and what was tried before. A new rule is added as a bullet here with its closing clause, and its record as a new entry at the end of `RULINGS.md`. `tests/rulings_check.js` holds this section and that file to each other.

- Every seat reads the draft in sparring and gives its own critique with the rating line first. The rating contract is the app's, exactly: the first line of every rating answer is `RATING: X/10`, uppercase, X from 1 to 10, never 7, nothing else on that line. Held by: tests/rating_contract_check.js, tests/packet_check.js.
- The rating leads every result. A ship, revise or kill verdict never replaces it as the headline. Scores are never averaged. Held by: tests/record_check.js, tests/board_check.js, tests/state_check.js.
- Sparring: each seat reads the draft alone; the person may put a focus question to every seat or a different one to each seat; seats may be shown each other's answers and debate the scores. Held by: tests/packet_check.js, tests/order_check.js.
- Battle (the `battle` command): the discussion of the structure and content of the draft. The round terms are the founder's: FQ, focus question (`fq:`), the same question put to every seat, nothing shared, the same as sparring's `question:`; N, navigation (`n:`), the same new guidance put to every seat individually, no other seat's answer carried; SN, synthesis navigation (`sn:`), each seat's synthesis shared with the others plus a new prompt, everyone answers and everyone reads each other; SFQ, synthesis focus question (`sfq:`), the crew's answers shared plus a new question. A seat line (`seat-N:`) is a note or question to one seat only; it may combine with `fq:` or any term; a round of seat lines alone goes to the named seats and the record marks the others "not asked". Wherever `sn:` is offered, `n:` is offered too. The count: `lib.roundTask` carries `n`, which of its kind the round is, counted per kind over the run's rounds for FQ, N, SN and SFQ, and `lib.taskLine` names the second and later with it (SN2, SFQ2) on the board's round line and in the record; `announce.js` counts the same from the rounds announced before (`lib.announcedOrdinal`) so the forming line agrees; the first of a kind keeps its bare name, and a run already on disk reads the same way once updated. Battle does not rerate on its own: a seat rates only when the person asks with `rerate`, and then the rating line is first; a battle round without `rerate` carries no RATING line and the record shows it as a critique. A new rating is held against the seat's latest earlier rating. Two sections: a battle packet that carries the other seats' answers (SN, SFQ, a plain synthesis round) asks for `Answer`, the reply to the task with the verdict line first (after the rating line when one is asked), then `To the crew`, the agreements, disagreements and questions to the other seats, each named by its model as the packet labels it and never by seat number alone, each section opened by a line holding only its label (`lib.SECTIONS_LINE` in the Contract, mirrored in the add-on's `crew-lib.js`; `sections: true` on the packet.built line); FQ, N, seat-line, first-round, sparring, debate and final packets ask for none; the checker holds the seat to both labels as to the rating line, a missing label sent back once, and on the second check (one whose first check failed, or one the add-on already cut on the seat's second overrun) noted (`section_notes`) and accepted, so a read is never lost over a label; the board frames the verdict from the Answer section; the add-on's system line says the two sections when the packet asks. The Contract follows the prompt: on a round with the person's prompt and no rating the packet asks for the answer as it asks and no verdict (`lib.PROMPT_FIRST_LINE`; the sharing form `lib.SECTIONS_LINE_PROMPTED` drops the verdict clause; `prompted` on the packet.built line); the verdict line stays on a rated round, where the number needs it, and on a plain round with no prompt; the person's prompt is the whole task, the plugin's own ask for a sharing round riding only when no prompt came, and the rewrite's rationale is under 120 words; a prompt that asks for a rewrite (a word list: rewrite, redraft, rework, revise, reword, "write it") gets the rewrite first, in full, between `=== REWRITE BEGIN ===` and `=== REWRITE END ===`, held by the checker like a label, framed on the board by its opening under a Rewrite badge with the whole rewrite under it, printed in the record; the add-on mirrors `SECTIONS_LINE_PROMPTED` and `REWRITE_LINE` and its system line says them (`packetRules` reads `verdict_first` and `rewrite`). The copy check: `check-answer.js` measures the share of a fenced rewrite's three-word runs found in each carried answer's rewrite (else its whole text); 0.6 or more is a copy, logged as `copy` {seat, model, round, share} on the answer.checked line and said on the terminal line; the board's badge reads "Rewrite · a copy of <model>'s", the record's cell "critique · copy of <model>"; the seat's own earlier turn is never a copy; the rewrite line says the rewrite is the seat's own. Held by: tests/packet_check.js, tests/announce_check.js, tests/rating_contract_check.js, tests/record_check.js, tests/sections_check.js, tests/rewrite_check.js, tests/board_check.js, tests/speak_check.js, tests/crew_check.js.

A Markdown file with YAML frontmatter (skills, commands, agents) keeps the frontmatter on line 1, because the loader reads it only there, and puts the comment on the line after the closing `---`. No other position is accepted.

## Directory constraints

Read on 2026-10-08 from the pre-submission checklist (claude.com/docs/plugins/pre-submission-checklist) and the publish page (claude.com/docs/directory/publish). LICENSE file or `license` field in plugin.json. README in the plugin folder over 40 words outside code blocks with at least three working example prompts. Every non-image file under 256 KiB. No lockfile beside a package.json at the plugin root. No top-level bin/. No .pdf, .zip or binaries. Any package launcher pinned to an exact version or absent. The plugin may be a subfolder. The manifest description follows the directory policy line "Descriptions must not include unexpected functionality or promise undelivered features" (Anthropic Software Directory Policy, support.claude.com). It promises only what parts 2 to 4 deliver.

## Test style

Plain Node, no dependencies, one file per concern named `*_check.js` (two exceptions, the live proofs, which need a running Claude Code and are never run by CI: `tests/seat_scope_live.js`, the seat's reach, and `tests/session_start_live.js`, the data folder the session-start hook is handed), a header comment that says what the test pins and how to run it, run from the repository root, exit 0 on pass and 1 on any failure, one printed line per failure. A test of a network client runs it against a fake server on localhost, never a real provider. CI runs every `tests/*_check.js` on each pull request and on main, then `claude plugin validate --strict` on both plugin folders and on the repository root; on a pull request the version-bump gate runs before the checks, and on a push to main the `tag` job (tags, then a Release for each tag without one) follows them. CI's `screen` job runs the screen's tests, `screen/tests/*_check.py` (Python, the same shape: one file per concern, exit 0 or 1, one line per failure), on the committed lock through uv; they build runs with the plugin's real scripts, so a change to how a run is seated or rendered reaches them too. One command runs the set CI runs, and a local pass is its exit 0 (Part 88, 2026-11-02; origin: pull request 136 passed the plugin's tests and the watchman locally and went red in the screen job): `node tests/run_all.js`, the plugin's tests, then the screen's through uv (a missing uv is a failure unless `--no-screen` says the skip is meant), then `claude plugin validate --strict` on the three folders when the CLI is on the PATH (skipped with a line when not). A session runs it before every pull request.
